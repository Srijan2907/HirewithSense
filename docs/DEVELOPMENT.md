# Development guide

This document is for people changing the code. It covers how the repository is organised, the
conventions we follow, and the day-to-day commands.

## Repository layout

```
apps/api            Fastify API
  src/config        environment schema (every variable is validated at boot)
  src/db            Drizzle schema, client, migrator, demo seed
  src/plugins       cross-cutting Fastify plugins: request context, security, auth, swagger, metrics, errors
  src/lib           small pure helpers: errors, crypto, redaction, time
  src/services      integrations: email, storage, audit, ai/*, runner/*
  src/modules       one folder per bounded context, each with routes.ts (+ service.ts)
  src/jobs          pg-boss queues, workers, scheduled sweeps
  drizzle/          generated SQL migrations (committed)
  test/             integration tests that run against a real Postgres
apps/web            React single-page app
  src/app           router, layouts, route guards, providers
  src/components    UI kit (ui/*) and shared widgets
  src/features      pages grouped by audience: public, auth, candidate, interview, coding, recruiter, dev
  src/lib           API client, auth store, query client, hooks, utilities, Monaco setup
packages/shared     Zod schemas, enums, scoring helpers and the consent text used by both apps
deploy/             nginx configuration used by the web image
scripts/            operational helpers
docs/               you are here
```

The API never imports from the web app and the web app never imports from the API. Everything
they share lives in `packages/shared` as source TypeScript; the API bundles it with tsup and Vite
compiles it for the web, so there is no build step for the shared package during development.

## Everyday commands

| Command | What it does |
| --- | --- |
| `pnpm dev` | API with hot reload (tsx watch) and the Vite dev server |
| `pnpm dev:api` / `pnpm dev:web` | one of the two |
| `pnpm typecheck` | `tsc --noEmit` in every workspace |
| `pnpm test` | Vitest in every workspace |
| `pnpm build` | API bundle to `apps/api/dist`, web bundle to `apps/web/dist` |
| `pnpm db:generate` | diff the Drizzle schema against the last snapshot and write a migration |
| `pnpm db:migrate` | apply pending migrations |
| `pnpm db:seed` | load demo data |
| `pnpm format` | Prettier over the repo |

## Contracts first

A request or response shape is defined once as a Zod schema in `packages/shared/src/schemas`.
The API attaches the schema to the route (`fastify-type-provider-zod`), which gives us three things
for free: request validation with structured error messages, response serialisation that drops any
field not in the schema (so a stray column never leaks), and the OpenAPI document served at `/docs`.
The web app imports the same schemas for form validation and the inferred types for everything
else.

When you add or change an endpoint, change the schema first. If the schema has `.default()` fields,
derive the update body from a base object without defaults (see `JobFields` in `schemas/job.ts`);
Zod 4 applies defaults through `.partial()`, which would otherwise reset fields on PATCH.

## Adding a module to the API

1. Create `src/modules/<name>/routes.ts` exporting a `FastifyPluginAsyncZod`. Put the business
   logic in a sibling `service.ts` when it is more than a handful of lines or is reused by a job.
2. Register it in `src/modules/index.ts` with a prefix.
3. Guard routes with `app.authenticate` (any signed-in user), `app.requireRole('recruiter')`, or
   `app.requireOrg('owner', 'admin')`. Resource-level checks (does this interview belong to the
   caller's organization?) live in the service, see `assertCandidate` and `assertRecruiter` in
   `modules/interviews/service.ts`.
4. Throw `AppError`s from `src/lib/errors.ts` (`notFound()`, `conflict()`, `gone()`, …). The error
   handler turns them into the standard `{ error: { code, message, details, requestId } }` envelope.
5. Record anything a recruiter would want in an audit trail with `audit({...}, req)`.
6. Write an integration test in `test/`. The helpers in `test/helpers.ts` create accounts and
   truncate tables; background jobs run inline in tests so you can assert on their effects right
   after the request returns.

## Database changes

Edit `src/db/schema.ts`, then:

```bash
pnpm db:generate --name describe_the_change
pnpm db:migrate
```

Commit the generated SQL and snapshot under `apps/api/drizzle`. Migrations also run automatically
when the API boots (`RUN_MIGRATIONS_ON_BOOT=true`), which is what the Docker image relies on.
Never edit a migration that has already been applied somewhere; add a new one.

Timestamps are `timestamptz`, ids are UUIDs generated by Postgres, and JSON columns carry a TypeScript
type through `.$type<...>()` so the rest of the code does not deal with `unknown`.

## Background jobs

pg-boss stores its queues in the `pgboss` schema of the same database, so there is no Redis to
run. Queues are declared in `src/jobs/boss.ts`, handlers in `src/jobs/index.ts`. Enqueue with
`enqueue('report.generate', { interviewId })`; pass a `singletonKey` when duplicates must collapse.
When `DISABLE_JOBS=true` (tests) the handler runs synchronously inside `enqueue`, and a failing
handler never fails the request that enqueued it, matching production semantics.

## Frontend conventions

- Server state goes through TanStack Query with keys from `qk` in `src/lib/query.ts`. Mutations
  invalidate the keys they affect. Errors surface as toasts automatically unless the query sets
  `meta: { silent: true }`.
- The access token lives in memory only (`src/lib/auth-store.ts`); the refresh token is an httpOnly
  cookie scoped to `/api/v1/auth`. `api()` in `src/lib/api.ts` retries once after a silent refresh
  when it sees a 401. Streaming endpoints use `streamSse()` because `EventSource` cannot send an
  `Authorization` header.
- Forms use react-hook-form with `zodResolver` and the shared schemas. For schemas with defaults,
  type the form as `useForm<z.input<typeof S>, unknown, z.output<typeof S>>`.
- UI primitives are in `src/components/ui`. They are hand-written around Radix so there is no
  generator to run; add to them rather than importing a second component library.
- Pages are lazy-loaded by the router. Add a route in `src/app/router.tsx` and a default-exported
  page component under `src/features/<area>`.
- Colours and spacing come from the tokens in `src/styles.css`. Dark mode is a class on `<html>`;
  use the `dark:` variant only when a token does not already cover the case.

## Testing

Integration tests are the main safety net. They spin up the real Fastify app with `app.inject`,
talk to a real Postgres, and exercise whole journeys (`test/flow.test.ts` goes from job creation to
a recorded decision). Unit tests sit next to the code they test (`*.test.ts` under `src`).

Set `TEST_CODE_RUNNER=docker` to also run the sandbox tests; CI does this on GitHub-hosted runners.

## Style

Prettier with the committed config, two-space indentation, single quotes, trailing commas. Prefer
small pure functions, explicit types at module boundaries, and comments that explain *why*. The
codebase is written to be read by the next person, not to be clever.
